From CRUD to hypermedia

A plan for refactoring ddd-web-api from a REST-ish CRUD API with intentional code smells into a command-based, hypermedia-driven, CQRS-separated REST API — and deleting the client-side knowledge that the CRUD design forced into existence.

elevator-api Java 21 · Spring Boot 4 elevator-ui Nuxt 4 shell + Datastar BFF deleted Media types 4 Slices 9 Structure vertical, not layered

01The thesis

Everything else in this plan follows from one observation about the current code.

The client owns a copy of the server's state machine. Not a cache of it — a second, independently maintained, silently diverging implementation of it.

And a copy of its URL space. Eleven paths, assembled from a hard-coded elevator id that is really a database primary key. The first copy is a matter of judgement; the second is a matter of fact, and §8 makes it falsifiable.

That is not a coding mistake anyone made. It is the inevitable consequence of a CRUD API: if the server will not tell the client what it may do next, the client has no choice but to work it out for itself. And to work it out, it needs to know the rules. And to know the rules, it needs to know the domain. So the domain leaks — into the BFF, into the store, into the components.

That question is exactly what hypermedia answers, and it is why the knowledge is currently smeared across three layers.

04Domain model

Pure Java. No Spring, no JPA, no Lombok. This is the one thing every slice shares — and it is shared precisely because it is the thing no single slice may own. Each element is annotated with the smell it eliminates.

Smells removed by construction

  • Primitive Obsession → Floor, Load, ElevatorId replace int/Long
  • Data Clumps → LandingCall, TravelPlan bind the travelling groups
  • Feature Envy → SCAN/LOOK ordering moves onto RequestQueue
  • Switch Statements → sealed ElevatorState; each state answers for itself
  • God Object → ElevatorService is deleted, not split
  • Model reuse → JPA entities confined to infrastructure/persistence
  • Long Method → recomputeState/recomputeMovement replaced by scheduled events
  • Shotgun Surgery → a validated Principal, built once at the security boundary, replaces re-parsed scope strings at every call site — §13 treats authority as a domain concept the same way this section treats a floor number

The timing change that unlocks everything

Today state is derived on read from stateSince plus elapsed wall-clock time. That is why the UI must poll, and why the two largest methods in the codebase exist.

Instead: when the aggregate commits to moving, it computes the arrival instant and a scheduler emits FloorReached at that time. Same physics, but now the server knows when something happens — which is precisely what SSE needs, and what deletes the derivation logic.

The original design note said "no ticking background job is needed". That was true for a polled CRUD API. It stops being true the moment the server has to push.

05States → affordances

The centrepiece. Pick a state and see exactly what the server would offer — and what it would silently omit. The client never learns these rules; it renders what it is handed.

Emergency recall pre-empts every state, and always settles into out-of-service.

Read the omissions, not the entries. In out of service there is no call-elevator affordance at all — so a rider client shows no call button without knowing what maintenance is. Today that same outcome requires a v-if in the component, a rule in the BFF, and a guard in the service.

06Commands, 1:1 with domain behaviour

CRUD is four operations over rows. The domain is ten behaviours over an aggregate. There is no total function from one to the other, and the shortfall gets paid for at every single call site.

Assignment versus message

A CRUD request asks what should this resource’s fields become? A domain request asks what should this elevator do? state = "movingUp" is an assignment; call(floor, direction) is a message. The assignment carries no why — and worse, it implies the elevator can simply become movingUp, when in the domain it becomes that only as a consequence of a call being scheduled. Field assignment invites states the domain has no legal path to.

That is the cognitive dissonance: anyone writing against such an API holds two models at once — the data model on the wire and the behaviour model in their head — and translates between them at every call. The translation is unwritten, undocumented, and lives only in people. So it drifts.

Intent is known, discarded, then guessed at

Two behaviours, one endpoint, and a hand-rolled dispatch to recover what was known all along.

When the answer is no

  

    A command can be refused, and refusal is where the CRUD shape hurts most: a rejected field assignment
    can only say the payload was wrong. The domain wants to say something else entirely — that the car
    is moving, that recall cannot be interrupted, that the load exceeds capacity.
  

  

    The hypermedia answer is that a refusal carries affordances too. Webber, Parastatidis
    and Robinson make the point in How to GET a Cup of Coffee: a conflict response should return the
    current state so the client can re-plan, and a forbidden response is an instruction to
    “look for other state transitions (links) in the response payload to make alternative forward
    progress”. Status codes stop being error codes and become a coordination protocol.
  

  

    Alongside that, RFC 9457 Problem Details gives the failure a type that is a URI —
    the same discipline already applied to rels, and dereferenceable to human documentation. With its own
    restraint clause worth honouring: “truly generic problems — i.e., conditions that might
    apply to any resource on the Web — are usually better expressed as plain status codes”.
    So “not authorised” needs no problem type, while “the car is in motion” earns
    one. The RFC even registers a type for the former case:
    about:blank, meaning the problem has no semantics beyond the status code,
    and the default when type is omitted.

Carrying affordances in a problem document

  

    problem+json has no standardised member for affordances, but it has
    a standardised mechanism for adding one. RFC 9457 §3.2 permits problem types to define
    extension members and requires that
    “clients consuming problem details MUST ignore any such extensions that they don’t
    recognize” — so an operations member is safe by
    specification rather than by convention. A generic client is obliged to skip it; ours is written to read
    it.
  

  

    
The RFC’s own flagship example already does this. Its out-of-credit problem
    carries "accounts": ["/account/12345", "/account/67890"], which the
    specification describes as listing “links where the account can be topped up”. That
    is an affordance in an extension member, in the document that defines the format. Carrying
    operations is not a compromise with the standard — it is the pattern
    the standard demonstrates.

    
§4 goes further and names the technique:
    “an extension might use typed links to another resource that machines can use to resolve the
    problem”. Our extension is the same operations array the state
    format already uses, with the same rel URIs, so a bespoke client needs no second vocabulary — and
    a bespoke client is what reads that format anyway.

  

  

    The RFC’s naming rules for extensions are worth honouring: names SHOULD begin with a
    letter, use only letters, digits and underscore so they survive the XML serialisation, and be three
    characters or longer. operations qualifies.
  


  
And Link headers underneath

  

    Extensions serve clients that were told about them. Link headers
    (RFC 8288) serve everything else: they are format-agnostic, attach to any response including one whose
    body a client cannot parse, and cost nothing to emit alongside the body.
  

  

  

    Lossy, and worth admitting: a Link header carries a rel and a target, not a
    method or a field list. It can say emergency recall is available and lives here; it cannot say
    POST it with these fields. The body is the complete answer; the headers are the floor beneath
    it, for clients that read neither Siren nor our extension.
  


  
Two details the RFC decides for us

  

    One field or several? RFC 8288 §3.5 answers this outright, with an example
    showing a comma-separated field and two separate fields and stating that the first
    “is equivalent to” the second. Neither is more correct, so the choice can be made
    on other grounds — and here there is one.
  

  

    
One field per link, because that is how they are produced. Affordances come from a
    list of contributors (§14), each of which knows about one operation and
    nothing about the others. Emitting a header per affordance lets a contributor append its own line
    without knowing whether it is the first, the last, or the only one. A single comma-separated field
    would mean assembling the whole set before writing any of it, which is a join across slices that exists
    only to satisfy a formatting preference the specification does not hold.

  

  

    What will the target return? The type parameter is
    “a hint indicating what the media type of the result of dereferencing the link should
    be”, and it reflects what the caller negotiated rather than what the failure happens to be.
    A client that accepts Siren gets a Siren document if it follows the link, even though the refusal that
    carried the link was problem+json. Note that the value must be quoted,
    since token does not permit /, and that a
    type is a hint only: it does not override the
    Content-Type that actually comes back.
  


  
One model, one more renderer

  

    None of this needs a special path through the code.
    Problem is a Representation that carries problem
    members alongside its affordances, and problem+json is simply a fifth
    renderer beside HTML, Siren, Hydra and the state format. RFC 9457 anticipates exactly this in
    Appendix C: problem details may be embedded in other formats “by translating the model of a
    problem detail… into the format’s conventions”, which is what a renderer is. The
    §11 completeness discipline applies unchanged: a refusal is a view of the
    events so far, and the alternatives it offers are the same affordance computation that produces a
    success.
  


  

    
Either way the client is told what went wrong, in domain terms, and what it may do
    instead — in a format it accepted, in the same rel vocabulary as every success. No error-code
    table, and nothing to interpret that it did not already have to understand.

  


  
Why this needs hypermedia, and hypermedia needs this

  

    

      
Commands alone are not enough

      

        Ten named operations that the client hard-codes is RPC. It is arguably worse coupled than
        CRUD, because there is more surface to couple to: ten paths and ten payload shapes instead of four
        verbs. Naming the operations fixes the vocabulary problem and leaves the discovery problem entirely
        untouched.
      

    

    

      
Hypermedia alone is not enough

      

        Affordances over a CRUD surface carry almost no information. If every operation is
        PATCH with a field bag, then “here are your available
        affordances” degenerates to “you may PATCH this” — which the client knew
        already. Affordances are only worth serialising when the operations are distinct and named.
      

    

  

  

    
The two ideas are load-bearing for each other. 1:1 commands make hypermedia worth having;
    hypermedia makes commands discoverable instead of hard-coded. This is why
    §16 scores “commands mapped 1:1” as only partly
    attributable to hypermedia — and why neither half is worth shipping without the other.

Where the documentation goes

  

    Fielding is prescriptive about this, and it doubles as a design test:
    “A REST API should spend almost all of its descriptive effort in defining the media type(s)
    used for representing resources and driving application state… Any effort spent describing what
    methods to use on what URIs of interest should be entirely defined within the scope of the processing
    rules for a media type.”
  

  

    So retiring the OpenAPI endpoint table is not an omission in this plan — it is the point. The
    documentation budget moves to the media types and the rel vocabulary, which are the things a client
    actually needs to understand and the only things it is allowed to depend on. If the reference
    documentation is a per-endpoint list, the API is a URI API wearing REST’s clothes.
  

  

    
This also answers the strongest objection to the whole approach — “the client still
    needs out-of-band knowledge of your media type, so what did hypermedia buy you?” Fielding’s
    reply is that REST does not remove prior knowledge, it relocates it: it is
    “far easier to standardize representation and relation types than it is to standardize objects
    and object-specific interfaces… there are fewer things to learn and they can be recombined in
    unanticipated ways while remaining understandable to the client.” Four media types and a rel
    vocabulary, learned once, versus eleven endpoints and their payload shapes, learned per API.

  

  

    The document that exists today. The CRUD API already publishes one:
    springdoc-openapi serves OpenAPI 3.1 at /v3/api-docs, with a Swagger UI at
    /swagger-ui.html. It is worth reading before deciding what to replace it with, because it
    is the clearest single exhibit of the problem. It lists twelve operations across ten paths and five
    schemas, of which Elevator is the entity itself — eleven properties including
    stateSince, departureFloor and targetFloor, internal scheduling
    state published as API surface. Not one property is marked required, so it constrains nothing. It
    declares no security schemes, so the two scope-gated operations appear open to anyone reading it. And
    every operation documents only a 200, so the refusals of
    §6 — the whole reason the domain is interesting — are invisible.
  

  

    What replaces it, best effort. The rewrite keeps publishing a document, aimed at the
    envelope: the media types, the Affordance, Field and Problem
    schemas, the rel vocabulary and the scopes. What it will not attempt is a per-state schema union.
    Eight states across four authority levels give twenty-eight distinct affordance sets, and seven of the
    eight states produce four different shapes under the same state value — which is the
    one thing an OpenAPI discriminator cannot switch on, since it reads a property of the
    payload and authority is never in the payload. The document describes what a response is made of; only
    the response says what may be done next.

The test that settles it

  

    Designing a True REST State Machine is blunt about this: to REST, URIs are
    opaque identifiers. /blogpost/47 is neither more nor less
    RESTful than /128ndoels-8asdf-12d5-39d3. What matters is not what the URI
    looks like — it is whether the client had to build it.
  

  

    Which turns a claim into an experiment. Can every URI in the API be randomised, and every
    client keep working?
  

  

  

    
Run the whole suite twice in CI: once with readable URIs, once with opaque per-run URIs. Anything
    that hard-codes a path fails immediately and by name. That converts “we are hypermedia-driven”
    from an architectural opinion into a build step — and it is the single cheapest guard against the
    coupling creeping back, because it fails the moment someone writes a URL by hand.

  


  
What stays readable, and what stays public

  

    
Tilkov has a name for what is left when URIs are documented rather than followed — a
    URI API — and near-listed “human readable URIs” as an anti-pattern in
    its own right before thinking better of it. His advice stands either way:
    “limit the time you spend on finding the perfect URI design (after all, they’re just
    strings), and invest some of that energy into finding good places to provide links within your
    representations.” The hours this repository’s history contains on endpoint naming were,
    by that measure, spent on the wrong problem.

  


  

    None of this argues for ugly URLs. Readable URIs are good for operators, logs and demos, and this
    project keeps them — the rule is that nothing may depend on their readability. Nor does it
    argue for hiding identifiers in general: floor numbers are domain identifiers and belong in the open,
    in field values, in the ubiquitous language. The rule is narrower and sharper than
    “hide the ids”:

In the aggregate

      

        ElevatorId remains a value object on the domain side — the
        aggregate needs an identity. What changes is that identity stops being the same thing as
        the resource’s identifier. Mapping between them becomes the web layer’s job,
        and the mapping is nobody else’s business.
      

    

  


  
One more rule, in the same spirit: no verbs in the URL either

  

    Opaque resource identifiers close one leak — the client stops being able to construct a
    URL. A second, smaller leak survives even a perfectly opaque identifier: 
    /elevators/{id}/open-doors, /elevators/{id}/close-doors,
    /elevators/{id}/car-calls, one URL per command, each one naming a verb.
    Every verb folded into a URL mints a new resource, and HTTP's uniform interface is a promise about
    one resource per URL — a fixed set of methods, each with fixed, method-defined semantics,
    not however many verb-shaped endpoints an API happens to need this month. Multiply the URLs and the
    uniform interface survives in name only: the predictable behaviour it exists to buy — a
    GET that any cache or intermediary may store and reuse without
    understanding this API, a PUT safe to retry blind because repeating it is a
    no-op, one identifier that means the same resource to every client and every proxy in between —
    now has to be re-learned per verb, because to HTTP each one is an unrelated resource, sharing nothing
    but a leading path segment: no common cache key, no common safety guarantee, no common anything. A URL
    names a resource, never a verb; a client that has memorized seven command URLs has memorized seven
    facts about the API's shape, exactly the thing following links was supposed to make unnecessary.
  

  

    The fix is the same discipline applied one layer further out: which behaviour a POST invokes is the
    request body's job — a "type" member naming the command
    — never the request line's. And the client still never has to know or construct that name: it is
    already sitting in a hidden field (Field.hidden("type", "OpenDoors"))
    among the affordance's own fields, so a client that merely echoes every field's value back never has to
    learn a single command name, exactly as it never has to learn a single URL.
  


  
Room to grow: three resources, not one inbox

  

    Naming the command in the body still leaves a question the URL itself must answer: which resource is
    this command about? Right now the answer is a single command inbox —
    POST /elevators/{id}, every command in the API funnelled through the
    elevator resource itself. That works today, but it is worth naming the requirement it will not survive
    unchanged: show the rider the last 10 calls made on this elevator. That is a
    GET on a collection of calls — and a single inbox has no such
    collection to GET, because "every command this API has ever grown" is not
    a coherent collection to list. A resource collection needs to be a collection of something.
  

  

    When that requirement arrives, the fix is to group commands by the resource-family they act on, each
    family becoming its own URL:
  

  

    
URLCommands

    
      

        POST /elevators/{id}/doors
        OpenDoors, CloseDoors
      

      

        POST /elevators/{id}/obstructions
        ObstructDoors, ClearObstruction,
            ReportLoad — obstruction in the broad sense: a light curtain
            trip and too much weight both keep the doors from behaving normally.
      

      

        POST /elevators/{id}/calls
        CallElevator, SelectFloor
      

    
  

  

    Each URL would still answer POST only at first; a later 
    GET /elevators/{id}/calls returning the last 10 calls is exactly the shape this grouping would
    make possible and a single inbox does not. Nothing about the rule from the previous section would
    change: a URL still names a resource, never a verb, and the command name still travels in the body's
    "type" member, echoed back from the same hidden field the client never had
    to learn. The only thing that would change is which resource each command belongs to.
  

  

    
This would cost one small thing in return: a request naming no command, or a command from a
    different family than the URL it was posted to, becomes a 400, not a 404 — the
    resource (the elevator) was found; the request just didn't name a command that resource answers to.
    From outside, "wrong command" and "command that exists but belongs elsewhere" would be made to look
    identical on purpose: a resource that only reveals which commands exist to a caller who already
    guessed right is not meaningfully more discoverable than one that reveals nothing.

  

  

    
Why this is safe to defer. Splitting one command URL into three, whenever it
    happens, should require precisely zero changes to elevator-ui's store: it
    already follows whatever href and fields an
    operation carries rather than any URL of its own. That is the entire payoff of building the hypermedia
    discipline in the first place — a client this indifferent to URL shape is exactly what makes it
    safe to leave this split for whenever the read-side requirement above actually shows up, rather than
    building it speculatively now.

  






  
09Change without versioning

  

    “No versioning needed” appears as one line in a table. That is the conclusion of an argument,
    not the argument.
  


  
A web API is not a library

  

    Versioning is uncontroversial for a statically linked library, and the reason is a time asymmetry that
    disappears on the web. You link against v1.0; the maintainer may then delete every line you depend on
    without harming you, and their v2.0 imposes nothing on you. Neither side pays for the other’s
    choices.
  

  

    A web API has no such symmetry. Every version still in use must be actively maintained —
    developed, patched, documented, deployed — by the server, for as long as any client uses it. The
    cost is entirely the provider’s, it compounds with each version, and it never ends. Which is why
    Fielding’s framing lands:
  

  

    
“What you are creating is not a new version of the API, but a new system with a new brand. On
    the Web, we call that a new website. Websites don’t come with version numbers attached because they
    never need to. Neither should a RESTful API. A RESTful API is just a website for clients with a limited
    vocabulary.”

    
— Roy Fielding, interviewed by
    Mike Amundsen; quoted in Asbjørn Ulsberg, API Change Strategy

  


  
What has a version, and what does not

  

    

      
Has a version

      
    
        
  • The client
    • 
        
  • The message format
    • 
        
  • The server implementation
    • 
        
  • The documentation
    •

  • Resources
    • 
        
  • Relations between resources
    • 
        
  • The API itself
    • 
      

    

  

  

    After Zdenek Nemec, as set out in API Change Strategy. The extension rules that follow are his:
    do not take anything away; do not change processing rules; do not make optional things required;
    anything added must be optional.
  


  
The rule hypermedia can break

  

    Those last two rules are absolute for a JSON API and negotiable for a hypermedia one —
    and this is a capability, not a philosophy. Because the server sends the form, it can introduce a new
    required field along with a default:
  

  

    
    
    
    
  

  

  

    
A client that has never heard of priority submits the form and
    sends priority=normal anyway. It stays correct without being
    modified, redeployed, or even told. A client that constructs its own request body cannot do this: it
    must learn the field exists, and until it does, its requests are invalid. That is the difference
    between “every client must be updated” and “no client need be.”

  

  

    In the affordance model this is one Field carrying a default and no prompt.
    The model holds it in every case; what differs is how much of it survives the rendering, and where each
    format puts the knowledge that makes it work. The four tabs above are not equivalent, and the ranking is
    not the one you would expect.
  

  

    
The three are not equivalent, and only one loses information. Siren carries the
    default cleanly: its field type is drawn from the HTML5 input types with
    hidden explicitly among them, and value supplies the default, so the unknowing
    client still submits priority=normal. The permitted floor list is the harder half, and
    the tab above shows the shape the community settled on rather than a degraded field: type
    of select, a value for the current choice, and an options array.
    None of it is Siren. The permitted field types are the HTML5 input types, and
    select is an element rather than an input type, so it is not among them;
    options is not a field attribute at all. Kevin Swiber opened the issue proposing this in
    August 2012 and it is still open, which is why every options array in the wild is a private
    extension that happens to agree with the others.

    
That cost is worth naming precisely, because it is not aesthetic. A client can only read this form if
    it was built knowing this server speaks the extension — which is out-of-band knowledge about a
    particular API, the exact thing hypermedia is supposed to remove. HTML has no equivalent problem because
    <select> was in the format from the start.

    
The bespoke format has it easiest, which is exactly the trap. It already
    distinguishes a list of permitted values from a single one, so the new field costs one scalar and no
    format change at all. That fluency is bought elsewhere: the reason an unknowing client still submits
    priority=normal is a processing rule saying clients echo back every key in
    expects, including keys they cannot interpret. Fielding would approve of the rule living in
    the media type — that is precisely where he says it belongs — but our media type has exactly
    one reader, so we own the client too, and no generic tool, browser or agent will ever honour it.

    
Hydra reaches for SHACL, which is the sanctioned answer rather than a workaround. Hydra Core
    deliberately declines to become a modelling language when a better one exists, and Hydra-SHACL
    Interoperability is a Community Group extension that an API announces through
    hydra:extension like any other. So sh:defaultValue and sh:in are
    how a Hydra API is meant to say this. The cost is not illegitimacy but surface area: a client must
    understand a second vocabulary to read the form, where an HTML client already knows what
    hidden and <select> mean.

  


  
Deprecation needs evidence

  

    Nothing can be removed safely without knowing whether it is used, and a CRUD surface gives poor
    evidence: one endpoint serves many intents, so the logs record that a row changed, not what anyone
    wanted. When every behaviour is a distinct rel at a distinct URL, “is anyone still calling
    this?” becomes a log query instead of a guess. The API can therefore shrink, which is the
    only thing that stops it growing forever.
  

  

    Ulsberg cites Jacques Dubray’s costing: point-to-point versioning runs around 45% more expensive at
    four concurrent versions than a compatible-change strategy — higher initial cost, lower total.

13Key-switch & authorization

  

    The key-switch is not a domain concept. Treating it as one is the first mistake; the second is letting
    the client reason about it. The third, and the one this section is built around, is treating
    authorization itself as a technical concern bolted on beside the domain rather than one more rule
    inside it — the position Bergh Johnsson & Deogun's Domain-Driven Security argues
    against directly: security is a set of business rules like any other, and belongs in the same model,
    the same ubiquitous language, checked by the same types, not in a filter that knows nothing of what it
    guards.
  


  

    
The key switch is a domain concept that is not an aggregate command. A car panel has
    a key switch; the ubiquitous language has a word for turning it. But turning it changes no elevator
    state — the aggregate has no keyInserted field, emits no event, and
    enforces no invariant about it. It is an affordance the server offers and a client may follow, whose
    effect is on authority rather than on the lift.

  


  
Following the key switch is an authorization challenge

  

    Which makes it the cleanest possible fit for the way HTTP already handles authorization. The
    insert-key affordance appears in the representation like any other. A client
    that follows it has not asked the lift to do anything — it has asked to be allowed to do more, and
    the server answers with a challenge:
  

  

  

    That is RFC 9728, Protected Resource Metadata, doing exactly what
    §8 asks of every other URL in this system: the client does not hard-code
    where the authorization server lives, or which scopes exist, or how to reach the token endpoint. It
    follows a link it was handed, reads the resource metadata, and finds the issuer from there.
  

  

    
The auth flow becomes discoverable hypermedia. Every argument in
    §1 applies unchanged to authorization: the client should not carry a second
    copy of where the authorization server is, any more than it should carry a copy of the state machine.
    A deployment can move its issuer, add a scope, or change grant types, and a conforming client follows
    along because it was never told any of it in advance.

    
And when the exchange completes, nothing about the elevator has changed.
    The next representation simply contains more affordances than the last one — which is what
    “the key is now inserted” means, expressed the only way this API expresses anything.

  


  
A validated Principal, not a re-checked token

  

    Domain-Driven Security's first pattern is to validate untrusted input exactly once, at the boundary,
    and represent the result as a domain type the rest of the system can trust by construction — a
    whitelist enforced by the type system rather than re-checked at every call site. 
    §8 already applies this to identifiers (ElevatorId, constructed
    only by UriResolver from a URI the server itself issued) and to domain
    values (Floor, Load reject an out-of-range
    primitive at the constructor, not downstream). Authority is validated the same way: the token completing
    the challenge above is exchanged, once, at the security boundary, for a Principal
    — and a Principal is the only thing any handler or
    AffordanceContributor ever sees. No handler re-parses a scope string; none
    receives a null principal it must remember to check for, because the type
    that reaches it was never allowed to be anything else.
  


  
Two client paths, one authorization model

  

    Most of this is already built. elevator-auth issues scoped tokens,
    elevator-api validates them by signature, and the two scopes are enforced
    separately — a maintenance token cannot recall, and a recall token cannot take the lift in or out
    of service. What the refactoring changes is not the protocol but who has to know about it.
  

  

    In the target architecture elevator-api serves both the HTML and the API
    from one origin. That matters: OAuth 2.0 for Browser-Based Applications (BCP,
    draft-ietf-oauth-browser-based-apps) states plainly that applications whose
    frontend and API share a domain do not need OAuth, and places such applications outside its scope. So
    the browser keeps a same-origin cookie — stateless, carrying the token rather than a key to it.
    Machine clients, which are genuinely separate parties, use OAuth directly. Both paths converge on the
    same construction: a verified credential goes in, one Principal comes out.
  


  

    
    
Two ways in, one validated Principal, one place that decides.

  


  
Keeping the cookie stateless

  

    A cookie that indexes server-side session state is a REST anti-pattern; a cookie carrying a token the
    server can validate without stored state is explicitly fine. The BFF pattern normally lands on
    the wrong side of that line, because “bind the token to a session” is its default advice. It
    does not have to.
  

  
    
    
  • The cookie carries the access token itself, or a signed assertion of its scopes
        — self-contained, verified by signature on each request, nothing stored.
    • 
    
  • HttpOnly, SameSite=strict, short TTL,
        scoped to the elevator resource. The browser still never reads it.
    • 
    
  • WithdrawKey clears the cookie. There is no server-side session to
        invalidate, which matches the domain: taking the key out is a local act.
    • 
    
  • Machine clients skip all of this and present Authorization: Bearer
        directly, which is the standardised means Tilkov prefers.
    • 
  

  

    
The trade is revocation. Statelessness means a token stays valid until it expires,
    because there is no server-side record to delete. Mitigated by a short TTL, and tolerable here because
    the credential stands in for physical key possession rather than an account — but on a system
    where a technician can be dismissed mid-shift, this is the wrong trade and a session is the right one.
    Choosing statelessness is a decision, not a default.

  


  
Scopes

  

    
ScopeHeld byGrants

    
      

        elevator:maintenance
        Technician, via the key-switch session
        enter-maintenance, exit-maintenance
      

      

        elevator:recall
        Technician — and, in principle, the building fire alarm panel
        trigger-emergency-recall
      

    
  


  

    
Why two scopes rather than one. In real installations these are not the same key
    switch. Fire recall is initiated by the building’s alarm system or a dedicated fire service key
    held by the fire brigade; the maintenance key belongs to the lift service company. A fire panel must be
    able to recall the car and must never be able to put the lift into maintenance or take it out
    — that would let a sensor fault strand the lift, or silently cancel a technician’s lockout
    while someone is on the car roof. The capability lattice is asymmetric, not nested.

    
Deferred by scope. The fire alarm panel is not built,
    because a sixty-minute slot cannot carry a third persona. It remains the intended holder of
    elevator:recall in isolation and the reason the scope exists — but
    until it is built, that scope has no isolated holder, and a sceptical reviewer is entitled to call it
    Speculative Generality. Better to concede that than to argue it.

  


  
What the client still knows that it should not

  


  

    The credential is safe and the session is standards-shaped, but the authorization model is
    still client-side. Worse, doing the right thing with the cookie forced the duplication: an
    HttpOnly cookie is by definition invisible to JavaScript, so the client can
    no longer infer its own privilege — it asks over a dedicated endpoint and caches the answer in a
    boolean the server already holds. Then it still decides, by itself, what that boolean unlocks.
  


  
Authorization is a domain rule, not a guard in front of one

  

    Scopes and affordances are the same idea one layer apart. A scope says what an actor may do; an
    affordance says what may be done now. Domain-Driven Security's second pattern is why these were
    never meant to be combined by the client: it objects to authorization living in a filter or an aspect
    that knows nothing of the domain it guards, because that forces the same rule to be re-expressed
    wherever it is enforced — exactly the Shotgun Surgery §1 diagnoses in
    MaintenanceController's three copies of “is this technician allowed to
    do this, right now?”. The fix is not a better filter. It is to let one predicate answer both
    questions at once:
  

  


  

    
Scopes never reach the client. One predicate, two inputs — the
    Principal and resource state — and a single answer: the form is there
    or it is not. AffordanceCatalog already collapses both into one predicate per
    §14's AffordanceContributor; a scope
    requirement on TriggerEmergencyRecall is not middleware standing in its way,
    it is part of what TriggerEmergencyRecall means, exactly as much as
    “not while already recalling” is. Add a scope requirement to an operation and no client
    changes, in any of the four media types. Without hypermedia, a scope change is a coordinated release
    across every client that ever learned which operations were privileged.

  


  

    
The command is already the right unit. §6's table
    notes that a command's authorization is “per command — which is what scopes already
    are”. That is not a coincidence: a command already names one domain behaviour, so it is also the
    natural, non-divisible unit to attach one authority requirement to. Field-level authorization
    (“per field, if you can even express it”) is hard precisely because a field is not a domain
    concept; a command always is.

  


  

    

      
Now

      
    
        
  • Client mirrors server authorization state in technicianKeyInserted
    • 
        
  • A GET /api/key round-trip exists solely to populate it
    • 
        
  • Which rels are privileged is hard-coded in v-if guards
    • 
        
  • When each is legal is a second, separate guard
    • 
        
  • The rule lives in three layers: component, BFF, controller
    • 
      

    

    

      
Target

      
    
        
  • Privileged affordances are present or absent in the representation
    • 
        
  • The client never learns which operations are privileged, or that scopes exist
    • 
        
  • No mirrored boolean, no GET /api/key, no v-if
    • 
        
  • Authorisation, resource state and business rules become one mechanism, not three
    • 
        
  • A rule change ships server-side alone
    • 
      

    

  


  

    
This is the Revisited article’s point made concrete: availability of an operation may vary by
    authorization, by resource state, by anything the server chooses — and the client’s job is only
    to react to what it is given, never to predict it. Securing a credential is table stakes. Collapsing
    authorization into the same mechanism as everything else, in the domain's own terms rather than a
    security configuration's, is the architectural move — and the reason a reviewer can read the
    aggregate and its contributors and see the entire authorization policy without also reading a
    separate security layer: there is only one place it is written down.

  







  
14Vertical slices

  

    One directory per domain behaviour, each holding everything that behaviour needs: command,
    handler, endpoint, affordance, tests. Not layers. High cohesion inside a slice, near-zero
    coupling between them.
  


  


  
The seam every slice plugs into

  

    This is the piece that makes vertical slicing pay off here. A slice does not register itself
    anywhere. It implements one interface, and the API starts describing it.
  

  


  

    
Note what is not there. No central list of features, no switch on
    rel, no registry to edit. AffordanceCatalog is a Spring-injected
    List<AffordanceContributor> that knows nothing about elevators.
    Adding a directory adds an affordance, which adds a form in HTML and an operation in all three
    JSON formats, with no other file touched.

    
That is the same argument as the client-side one, pointed the other way:
    the client hard-codes no knowledge of the API; the framework hard-codes no knowledge of the features.

  


  
Where the paradigm has to bend

  

    

      
Sliced

      
    
        
  • Commands, queries and their handlers
    • 
        
  • HTTP endpoints and URI shapes
    • 
        
  • Affordance descriptors and availability rules
    • 
        
  • Read models and the projections that fill them
    • 
        
  • Tests — each slice is independently testable
    • 
      

    

    

      
Deliberately shared

      
    
        
  • The Elevator aggregate and its value objects
    • 
        
  • The domain event hierarchy
    • 
        
  • The four renderers — cross-cutting by media type, not by feature
    • 
        
  • Persistence adapters
    • 
      

    

  


  

    
Slice the shell, share the core. Isolation earns its keep the further out you go and
    costs you the further in. At the edge — endpoints, payload shapes, affordances, read models
    — independence is almost free and duplication is cheap. At the centre, where the invariants live,
    independence is duplication, and duplication is drift.

    

      This is the same boundary Onion and Hexagonal architecture draw, and the same one
      “Functional Core, Imperative Shell” draws for different reasons. Vertical slicing is a
      statement about the shell. It was never a licence to shard the core.
    

    

      The domain makes the case concretely. Emergency recall pre-empts all states and clears the
      queue. Maintenance rejects calls that CallElevator would otherwise accept.
      Overload invalidates a car call belonging to another slice. Give each slice its own elevator state and
      those rules get restated per slice — which is the failure this refactoring exists to remove,
      rebuilt on the server instead of the client. The aggregate is shared because it is the thing
      no single slice may own.
    

  


  

    
AGENTS.md needs surgery, not a touch-up.
    Its standing rule — "organize by type, not by feature… do not reorganize into
    feature/domain-based packages (e.g. calls/,
    doors/)" — is now exactly inverted. So are
    "do not refactor away the code smells", "do not unify the two REST representations", and the entire
    BFF description. Replacements: one directory per behaviour; the client may not hard-code URLs or
    domain constants; new behaviour means a new slice, never a new flag.

  







  
15Roadmap

  

    Refactored in place, slice by slice, mirroring the original build order — so the commit history
    reads as a direct before/after. One commit per slice, each naming the smell removed, followed by lint
    and tests for both projects, then a pause for review.
  

  







  
16What hypermedia actually buys

  

    This refactoring carries two ideas, not one. Attributing each improvement to the right one is what
    keeps both arguments honest — and a “no” in the REST column is very often a
    “yes” in the DDD column, which is a win, not a deduction.
  


  

    
The trap. Bundle a dozen improvements into one refactoring, ship it, and every
    improvement gets attributed to whichever idea was on the slide. Then someone asks “couldn’t
    you have just fixed that?” — and the answer is yes, and the whole argument wobbles. Scoring
    each row against both ideas costs nothing and forecloses the objection.

  


  

    
ImprovementREST?DDD?Why

    
  


  

    
Reduced to one sentence each: DDD moves the rules to the
    place that owns them; hypermedia stops the client keeping a second copy.

    
Every “core” row restates the second — legality,
    authorization, permitted values, available transitions, versioning, and what happens to a client when
    the domain changes. Every DDD “yes” restates the first. Note how many rows carry both: that
    overlap is not double-counting, it is the reason the two ideas are worth presenting together rather
    than as separate talks.

    
Only two rows are “no” twice, and both are things worth doing
    anyway. Nothing here is wasted work — it is just work that belongs to one argument or the other.

  


  

    

      
Why still do the orthogonal work?

      

        Because the talk is Domain-driven web APIs, and the aggregate is what makes the affordances
        computable in the first place. AffordanceCatalog can only ask
        “what may happen next?” because a sealed ElevatorState can
        answer it. Bolt hypermedia onto the God Object and you get a fifth place where legality is decided,
        not one.
      

      

        The DDD work is the enabler. It is just not the payoff.
      

    

    

      
The honest CRUD counterfactual

      

        A CRUD API with a clean aggregate, SSE push and vertical slices would be a
        good application. Better than what is in this repository today by a wide margin.
      

      

        It would still ship a client that hard-codes fourteen URLs, duplicates the floor count and the travel
        timing, and re-derives which buttons are legal. That residue is the whole subject of the talk.
      

    

  







  
17Agents, tools and ontologies

  

    A digression, and deliberately a general one: nothing below is about lifts, or about this refactoring.
    The question is whether a hypermedia API with a shared vocabulary would drive an AI agent better than
    the protocols built for the purpose — MCP between an agent and its tools, A2A between agents. No
    agent works this way in production today, so this argues a fit rather than reporting a result.
  


  
What a capability document can and cannot depend on

  

    Every one of these protocols has to answer the same question — what may the caller do?
    — and each answers it with a document produced independently of any particular moment. That forces
    a choice about which things the answer is allowed to depend on, and all three drew the line in a
    different place.
  

  

    

      Tells the agent what it may do
      Varies by state
      Varies by authority
      Varies over time
      Terms globally defined
    

    
      

        OpenAPI §7
        Yes via discriminator
        No authority is not in the payload
        No a document has no clock
        No schema names are local
      

      

        MCP tools/list

        Yes credentials are per-request input

        No tool names are free text
      

      

        A2A Agent Card

        Partly only through the extended card

        No skills are id, name, description, tags
      

      

        A JSON-LD hypermedia representation
        Yes
        Yes
        Yes
        Yes
      

    
  


  

    
MCP draws its line in a surprising place. One sentence carries three of the columns:
    the tool set “MAY be empty and MAY change over time… but MUST NOT vary per-connection or
    as a side effect of other requests on the connection”, and it “MAY vary by the
    authorization presented on the request”. So the list may change for reasons outside the
    conversation — the clock, the caller’s credentials — and must not change because of the
    conversation. What the agent has already done is the one thing that may not affect what it is offered
    next, which is precisely the dependency any stateful domain is made of.

    
A2A draws its line earlier still. The Agent Card at
    /.well-known/agent-card.json describes an agent’s identity and skills, not the state of
    any work in progress, and it is expected to change infrequently — cached with
    Cache-Control and ETag, with no notification when it does. Authorization is
    handled by a second document, the extended card, which “MAY” reveal additional
    skills to an authenticated caller. A2A does define a task state machine, with
    INPUT_REQUIRED and AUTH_REQUIRED among its states, but a state is not a set of
    affordances: it says the work is stuck, not what may now be done about it, and the specifics arrive as
    prose for the model to read.

  


  
Three costs a catalogue pays and a representation does not

  

    Context. A catalogue is charged on every turn. Each skill or tool description occupies
    the window whether or not it can be used right now, and the preconditions are the model’s to hold.
    A representation carries only what is currently possible, so the agent is never told about an operation
    it cannot take, and never has to be told why.
  

  

    Refusal. Omission covers what is unavailable but not what was attempted. MCP reports a
    failed call as isError with text, explicitly so the model can “self-correct and
    retry”; A2A leaves it to a task state plus an agent message. In both cases the recovery path is
    prose, and the agent’s next move is a guess informed by reading it. A problem document with the
    permitted operations attached is the same information, machine-readable.
  

  

    Staleness. Both protocols make the client responsible for noticing that the answer has
    moved on. MCP at least offers notifications/tools/list_changed, though it signals that the
    catalogue is stale rather than carrying what replaced it; A2A has no equivalent for its card. A
    representation cannot drift from the thing it describes, because it is produced by the same request that
    reads it.
  


  
The vocabulary argument, which is the strongest one

  

    In all three protocols the names are local strings. An MCP tool is called whatever its author called it;
    an A2A skill is an id, a name, a description and some
    tags, written for a model to interpret. Nothing intrinsic to a property named
    table says whether it is a dining table or a data table, and the agent resolves that by
    guessing from context or by asking. In JSON-LD every term is an IRI, so the question cannot arise.
  

  

    Where that IRI comes from a genuinely shared vocabulary, it buys a second thing worth more than the
    first. The meaning is not merely unambiguous, it is already known: an agent trained on the open
    web has read schema.org, so Order, OrderInTransit and CancelAction
    need no introduction. The API ships no definitions, spends no context explaining itself, and needs no
    clarifying round-trip before the first useful call. A bespoke vocabulary of equal quality buys the
    unambiguity and none of the prior knowledge.
  

  

  

    The third of those is doing something the other two structurally cannot. It is an affordance, valid at
    this moment for this caller, expressed in terms defined outside the API by a vocabulary the agent already
    holds — and schema:potentialAction is not a hypermedia bolt-on, it has been in
    schema.org for years. The pieces of this argument are not hypothetical; they are simply not yet wired
    together.
  


  

    
Three ways to oversell this. The context saving is real only for vocabularies a model
    already knows; a bespoke ontology still removes ambiguity, but it is exactly as unknown as a bespoke tool
    name. Models are fine-tuned for tool-calling and not for hypermedia traversal, so today the ergonomics
    run the other way regardless of which design is better. And following affordances costs round-trips that
    a catalogue front-loads. The defensible claim is that hypermedia removes a class of error — the
    agent attempting what the domain forbids, or misreading what a term meant — not that it is
    currently the cheaper or easier path.

  


  
If the tooling were equal

  

    That last sentence invites the obvious question: suppose it were. Suppose a JSON-LD format — Hydra,
    or something shaped for agents on top of it — had the client libraries, the fine-tuning and the
    installed base that MCP acquired in a year. Would that world be better than this one? The useful way to
    answer is to sort the objections by whether adoption would dissolve them, and three of the four are not
    what they look like.
  

  

    
Objection todayVerdictWhy

    
      

        Models are trained for tool-calling
        Dissolves
        An artefact of what existed to train on, not of either design. It describes the present, and nothing else.
      

      

        Following affordances costs round-trips
        Inverts
        MCP may not change its tool list as a consequence of a call, so after acting the agent infers what changed from prose. A hypermedia response to that same action carries the resulting state and the affordances that now apply. One request each; only one answers the question the agent actually has.
      

      

        JSON-LD is verbose
        Remains
        Reduced but not removed. Compaction against a known context turns IRIs back into short terms, and the affordance set is smaller than a catalogue — but an interoperable identifier will always cost more characters than a local name.

        Remains
        And this is the real limit. It is a property of the domain, and no amount of adoption touches it.
      

    
  

  

    That last row is worth dwelling on, because MCP’s own framing marks the boundary honestly: it
    describes tools as primitives with well-defined structured inputs and outputs, often stateless.
    For a stateless capability — search, arithmetic, translation, fetching a document — there is
    no state for a representation to reflect and nothing for affordances to add. A catalogue is not a
    compromise there; it is the correct shape. The gain appears only where a resource has rules about its own
    sequence, and for that half MCP was never claiming to be the answer.
  

  

    
Which means the sharpest version of this argument is not aimed at MCP. It is aimed at
    A2A. Agents are the stateful, long-running, opaque things in this picture — A2A says so itself,
    describing peers that reason, plan and hold state across multi-turn tasks — and it asks them to
    advertise what they can do through a cached static document that is expected to change infrequently and
    announces nothing when it does. The mismatch between what is being described and how it is described is
    widest exactly where the collaboration is richest.

  

  

    So the honest answer is that such a future would be better for an identifiable half of the problem, for
    reasons that survive the tooling gap closing, and no better at all for the other half. What stands in the
    way is not design. Hydra has been a Community Group document since 2013 and remains one; MCP went from
    introduction to broad implementation in about a year. Shared vocabularies do not appear because they are
    a good idea — schema.org exists because search visibility paid for it, and nothing comparable
    currently pays for an ontology of business operations. The pieces are specified and unassembled, which is
    a problem of incentives rather than of protocols, and therefore not one a better protocol can solve.
  







  
18The honest limits

  

    The sharpest objections to this plan come from hypermedia’s own advocates. Two of them land, one
    is answered by scope, and one is simply wrong — and saying which is which is more useful than
    conceding all four.
  


  
The scale objection, and why the elevator is still the right demo

  

    Fielding is explicit that the constraints are not free:
    “REST is software design on the scale of decades… Many of the constraints are directly
    opposed to short-term efficiency”, and
    “REST is intended for long-lived network-based applications that span multiple organizations.
    If you don’t see a need for the constraints, then don’t use them.”
  

  

    
The binding constraint here is sixty minutes, not nine floors. A system that genuinely
    warranted REST on Fielding’s terms — federated, multi-organisation, decade-lived —
    could not be explained, let alone refactored on stage, in a conference slot. The elevator is chosen to
    be small enough to hold in your head and still large enough to break CRUD: real invariants, a
    pre-empting state machine, two personas, and behaviours that cannot be expressed as field assignment.

    
So the correct claim is not “this system needs REST”. It is
    “this system is the smallest one on which the need becomes visible”. Anyone extrapolating
    the economics from nine floors to their own estate should be told to do the sums again.

  


  
The agency objection, and why it does not hold

  

    Carson Gross argues that “a system satisfying HATEOAS is wasted if the hypermedia isn’t
    being consumed by something with agency. Humans are that thing”, since code
    “can’t reasonably decide what to do in the face of new and unexpected actions”.
    The premise is true. The conclusion does not follow.
  

  

    “Cannot exploit an unknown affordance” is not the same as “gains nothing from
    affordances”. A machine client that knows a rel and a media type in advance still gets four things
    it cannot get from a documented endpoint, none of which require agency:
  

  
    
    
  • Late binding. It never holds a URL, so the server may reorganise its entire URI
        space without coordination.
    • 
    
  • Conditionality. It is told whether recall is available now, instead of
        attempting it and interpreting a 409.
    • 
    
  • Field discovery. Permitted values arrive with the affordance, and a newly required
        field can arrive with a default it never heard of.
    • 
    
  • Ordering. Which transition comes next is answered by the representation, so the
        client need not encode the state machine to know when to act.
    • 
  

  

    
The difference between a browser and a fire alarm panel is breadth of vocabulary, not the
    presence of agency. A human following a button marked “Checkout” is not inventing
    semantics either — they are recognising a known affordance, which is exactly what the panel does
    with trigger-emergency-recall. And the alternative is not neutral: a machine
    client that does not consume hypermedia must hard-code the URL and the state machine, which is
    the precise failure this entire plan exists to remove.

    
What Gross is right about is narrower: a new rel goes unused by a
    machine until someone teaches it. But it does not break it — and “does not
    break” is the benefit being claimed. That concession was safe when every machine client was a
    hard-coded script, which is worth revisiting now.

  


  

    
The premise has since expired. The argument is not really about hypermedia; it is
    about the world. It holds exactly as long as “something with agency” and
    “a human” pick out the same set, and they stopped doing so after it was written. An
    agent that reads a rel it has never encountered, together with a title and a list of fields, and then
    decides whether that affordance serves its goal, is doing the thing the argument says code cannot do
    — and deciding what to do in the face of new and unexpected actions is close to a job
    description for these models.

    
This inverts the objection rather than rebutting it. Gross’s reasoning is sound: hypermedia
    repays a consumer capable of interpreting what it is handed, and there was only ever one such consumer.
    The supply has changed, not the logic. So the narrow concession above shrinks too — a new rel need
    no longer wait for someone to teach a client, because the client can read it — and the four
    benefits listed earlier stop being a consolation prize for clients that lack agency and become the floor
    beneath one that has it.

    
The catch is the mirror image, and it is the reason
    §17 cares so much about vocabulary. What a new rel now waits for is not
    teaching but unambiguity: agency without a shared vocabulary produces a client confident enough
    to act on a term it has misread. A human unsure what table means asks someone. An agent
    unsure what it means proceeds.

  


  
Where hypermedia genuinely yields

  

    Gross’s other caveat is sound and this design already respects it. Hypermedia is a poor fit for
    UIs whose interdependencies cannot be resolved at render time, for offline operation, and for
    very frequent state updates. A lift car animating between floors is the third case exactly,
    and no sane design re-renders a fragment per frame. His guidance is that
    “it is typically easier to embed SPA components within a larger hypermedia architecture, than
    vice-versa” — which is precisely the shape §12 arrives at:
    server-driven affordances everywhere, the shaft animation left to the client. In the event, the demo's
    version of this is deliberately minimal: not a stateful Vue component re-deriving position from a
    store, just a CSS transition whose two endpoints (start floor, end floor) and duration
    (travelSecondsPerFloor) are read directly off the DOM
    elevator-api already rendered, every time it changes. No signal, no store,
    no polling -- the browser's own CSS engine does the interpolating, exactly the part Gross is right
    that hypermedia itself should not be pushing sixty times a second.
  


  
Data APIs and application APIs want different things

  

    Gross’s constructive point stands and supports this plan rather than undermining it: a
    general-purpose data API optimises for stability and machine consumption, while an application API is
    tuned to one front-end and churns with it. That is an argument for content negotiation. The
    HTML representation may be shaped by the rider console without apology, precisely because Siren and
    Hydra carry the machine case separately.
  


  
Where this design breaks its own rules

  

    Stefan Tilkov’s REST Anti-Patterns lists eight ways to get RESTful HTTP wrong. This plan
    is clear of six — it does not tunnel through GET, does not funnel every
    intent through one POST URI, does not ignore status codes, does not forget
    hypermedia, and negotiates four media types rather than one. Two require an answer.
  


  

    
Cookies carrying session state. “Using cookies to propagate a key to some
    server-side session state is another REST anti-pattern… It’s session state that is
    disallowed due to scalability, reliability and coupling reasons.” Tilkov grants an exemption
    for “an authentication token that the server can validate without reliance on session
    state” — which is the exemption §13 now deliberately
    stays inside.

  


  

    
Self-descriptiveness. “Every time you invent your own headers, formats, or
    protocols you break the self-descriptiveness constraint to a certain degree.” By that measure
    application/vnd.elevator.state+json is the weakest of the four, understood by
    nothing that has not read our documentation.

    
It is in the plan as a teaching device and a transitional step, not
    a recommendation: it is the format from the State Machine article, it fits on a slide, and its
    operations array can be read aloud in one breath where a full Siren document
    cannot. Its job is to make the concept legible, and then to be replaced by Siren or Hydra. Ship the
    standards; keep the bespoke one for the projector.

  


  

    
None of this retracts the thesis. It bounds it. The client should not duplicate the
    server’s state machine — that holds at any scale, and it is why the refactoring is worth
    doing even here. What does not follow from a nine-floor lift is the economic case, and a talk
    that claims the economics of a decades-long federated system for a single building invites exactly the
    scepticism hypermedia already suffers from.

  







  
19Open questions

  
Two decisions worth settling before slice 0 begins, each with a proposal attached.


  

    
Keeping Nuxt is the weakest link settled, build in slice 0

    

      After slice 8, elevator-ui renders a <div>
      and a stylesheet. It buys a same-repo before/after diff and preserves the Playwright suite. It costs
      cross-origin SSE, CORS with credentials, and a build toolchain serving one static page.
    

    
Decided: put both behind one origin, in slice 0. A Caddy
      reverse proxy in docker-compose, about a dozen lines, serving the whole
      application on one port with /elevators and
      /elevators/* routed to elevator-api and
      everything else to Nuxt. Every cost above disappears at once: no CORS, no
      withCredentials, no SameSite negotiation, and
      the browser-based-apps BCP’s same-domain reasoning applies for real rather than by assertion.
      The before/after diff survives intact, and the deployment gains a layer that is itself a REST
      talking point: an intermediary that can act on the uniform interface without understanding the
      application.
    


    

      
Not before slice 0, though. Two thirds of the case above is future tense. Today the
      browser only ever calls /api/* on the BFF, so there is no origin to cross
      and nothing routes to /elevators/* at all — installing the proxy now
      would ship a rule that serves no traffic, which is Speculative Generality in a repository built to
      demonstrate it. The one present-tense benefit — keeping the API off the network — has
      been taken separately by binding the published ports to 127.0.0.1, so
      the proxy can travel with the slice that needs the rest.

    


    
Will it leak anything? No — and it closes a
      hole that is open today.

    
    
      
  • The shared secret lives in runtimeConfig.technicianKey and
          elevator.technician-key. Neither is served by any route, and the proxy
          does not move them.
    • 
      
  • There is no Actuator on the classpath. This matters more than it sounds:
          /actuator/env and /actuator/configprops
          would publish elevator.technician-key verbatim. The rule the proxy
          config must follow is therefore allowlist the paths you mean — never
          wildcard a whole service — so that adding a dependency later cannot quietly publish a
          management surface.
    • 
      
  • No H2 console, no devtools. The API’s entire surface is ten paths, all domain endpoints
          plus /health.
    • 
      
  • The technician cookie must be narrowed from Path=/ to
          Path=/api as part of the same change. Every route that issues
          or checks it lives under /api, and a /
          cookie under a shared origin would be attached to /elevators/* too
          — reaching a service with no use for it and landing a valid credential in its access log.
          Correct today, so it is a prerequisite rather than a fix.
    • 
    


    

      
The BFF is not a security boundary, and the proxy is what would make that structural.
      docker-compose now publishes on
      127.0.0.1 rather than every interface, so the bypass is no longer
      reachable from the network — but it is still reachable from the host, and
      elevator-api is still independently addressable, so every BFF check
      remains bypassable by anyone who types the port. Nothing is
      exposed by that — privileged endpoints still demand the Bearer token, so direct access buys
      only the rider actions that are public anyway — but it does mean
      requireTechnicianKey is a UX affordance, not a control. The real control
      is requireValidKey in MaintenanceController.

      
Behind a proxy both service ports stop being published at all and the
      proxy becomes the only ingress, which closes the bypass rather than merely narrowing it. Binding to
      loopback was the cheap half of this and is already done; the proxy is the rest.

    


    

      One thing a shared origin will introduce, once elevator-api accepts the
      cookie itself: state-changing requests authenticated by a cookie become CSRF-able.
      SameSite=strict is what answers it, and it is already set — but it
      moves from incidental to load-bearing, and should be treated as such.
    

  


  

    
Slice 0 is front-loaded

    

      Four renderers plus a domain rewrite before a single feature moves. That is a long time on stage
      before anything visibly works.
    

    
Proposal: ship HTML only in slice 0, and add the JSON formats as
      slice 3.5. The affordance model is unchanged; only renderers are added. It shortens the
      opening, and it converts the weakest part of the argument into the strongest demonstration of it
      — “here is a new media type, and the domain layer has no idea it happened.”
      Doing it later also lets the H-factor comparison in §7 be shown against
      running code rather than as a table.
    

  


  

    
Settled by scope, not by argument

    

      Two things are deliberately unbuilt and should be labelled as such rather than defended: the fire
      alarm panel that would hold elevator:recall in isolation, and the
      separate authorization server that would then have a client worth serving. Both are correct designs
      that do not fit in the slot.
    

    

      The risk of deferring is specific and worth stating once on the day: until the panel exists, the
      second scope has no isolated holder, and a sceptical reviewer is entitled to call it Speculative
      Generality.
